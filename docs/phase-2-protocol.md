# Phase 2 — implemented desktop wire contract

> Historical v0.2.0 scope/evidence. For current v0.3.0 files and health capability additions, see [Phase 3 implementation](phase-3-implementation.md) and [file protocol](phase-3-protocol.md).

[Implementation](phase-2-implementation.md) · [User workflow](pairing-and-recovery.md) · [Broader protocol roadmap](06-communication-protocol.md)

This is the implemented **connection-only v1 subset**. The larger protocol document contains planned file, event, transfer and chat contracts; those routes do not exist in this build.

## Three separate authorities

| Channel | Authentication | Allowed authority |
|---|---|---|
| Local OS IPC | Owner SID/workspace-scoped Named Pipe; same-UID Unix development socket | Explicit local-owner commands. |
| Temporary bootstrap HTTPS | Server certificate/public-key identity pinned by the code; one-time invitation secret | Submit one bounded certificate claim only. |
| Normal HTTPS | TLS 1.3 mutual certificates; exact allowed pins; active/temporary state and current epoch checked | Pending proof/ack, or active connection health and permission metadata only. |

The development HTTP bridge is a feature-gated, token-protected loopback owner adapter behind a same-origin Vite proxy. It is **not** a LAN peer route and is absent from default builds.

## Identity and TLS profile

- Transport key: P-256 ECDSA, generated by the library with secure OS randomness.
- Generic self-signed certificate: `narada.local` SAN, digital-signature usage, server/client authentication EKUs. No workspace label in the certificate.
- Certificate fingerprint: lowercase SHA-256 of DER certificate bytes.
- Device ID: lowercase SHA-256 of DER SubjectPublicKeyInfo. This is distinct from the certificate fingerprint.
- Certificate syntax, P-256 key profile, self-signature and current validity are checked. Exact pins are checked in addition to WebPKI validation and rustls handshake-signature verification; there is no accept-all verifier.
- TLS 1.3 only, HTTP/1.1 ALPN, no 0-RTT, no session resumption, no server tickets. A reconnect proves the key again.
- Generated certificates have a ten-year validity window with a small creation-time clock allowance. Expiry does not silently rotate keys. An in-place rotation UX and its security qualification remain future work.
- Literal private IPv4 or loopback endpoints only. No DNS, credentials, URL paths, public/multicast/link-local addresses, redirects or port zero for a remote endpoint. Outbound sockets bind the selected local address.

## Invitation

The owner gets a JSON text code once; the QR encodes those exact bytes. Fields:

| Field | Meaning |
|---|---|
| `format` | `narada-pairing` |
| `version` | `1` |
| `invitation_id` | UUID |
| `token` | 32 random bytes encoded as 64 hex characters; secret |
| `endpoint` | Temporary bootstrap IPv4 address and port |
| `fingerprint` | Expected host certificate fingerprint |
| `device_id` | Expected host public-key identity |
| `name` | Display label only; not authentication |
| `expires_at` | UTC RFC3339 display/clock check |

Only the token hash is retained by the host. Snapshots, activity and diagnostic exports do not contain the token or full code. Maximum code size is 4096 bytes. Only one invitation is live at a time; lifetime is **120 seconds**, enforced by a monotonic deadline. A rejected token does not consume it; a successful claim consumes it even if approval never follows. Claim replay, including the same claim, is rejected.

The UI erases its code when closed/expired/completed. Clipboard contents are not a revocation mechanism: the server's expiry/consumption is authoritative.

## Handshake state machine

```text
owner enables selected-interface networking
  → creates one-use invitation and temporary bootstrap listener
  → joiner pins host certificate + public-key identity before sending the token
  → host accepts one certificate claim, bound to attempt UUID
  → submitted pin is temporarily eligible ONLY for proof/ack
  → joiner completes mTLS with that private key and sends proof
  → owner compares requester fingerprint and explicitly approves grants
  → joiner persists host as pending (not active)
  → joiner sends final mTLS acknowledgement
  → host durably commits active trust, then returns confirmation
  → joiner activates its pending record and exchanges authenticated health
```

No trust is activated by discovery, certificate submission, the UI comparison checkbox alone, or owner approval alone. An acknowledgement without proof/approval fails.

The host's successful final acknowledgement is idempotent for the same active certificate, attempt and invitation. It does not increment the grant revision or duplicate a peer. A joining-side pending record can retry that acknowledgement after a lost reply/restart. If the host never committed and its invitation expired/restarted, recovery fails closed and a fresh approved pairing is needed.

While waiting for approval, the joiner can renew an interrupted proof connection using the same pending pin and attempt; it does not replay the bootstrap token. The outer invitation deadline still applies. Explicit cancellation uses a durable attempt tombstone.

## Routes

All accepted messages are bounded JSON `POST` bodies with `Content-Type: application/json`. Unknown fields and compressed bodies are rejected. Query strings and absolute-form URLs are not accepted.

| Listener | Route | Request | Success |
|---|---|---|---|
| Bootstrap only | `/pair/v1/claim` | `hello`, invitation/attempt IDs, token, certificate Base64, self-reported name/platform | Protocol agreement, echoed attempt, normal API port, public host certificate and label. |
| mTLS | `/pair/v1/prove` | `hello`, invitation/attempt IDs | `awaiting_owner` or `approved`, with this attempt's grants. |
| mTLS | `/pair/v1/ack` | Same proof envelope | `active` only after durable approved activation; idempotent thereafter. |
| Active mTLS | `/api/v1/hello` | `hello` object | Authenticated connection/permission metadata. |
| Active mTLS | `/api/v1/health` | `hello` object | Same validated health metadata. |
| Active mTLS | `/api/v1/capabilities` | `hello` object | Same bounded connection-only metadata. |

`hello` is:

```json
{
  "version": 1,
  "capabilities": ["connection.health", "connection.permissions"]
}
```

Both listed capabilities are mandatory. Optional unknown offers do not enable an operation; responses advertise only the supported subset. Any protocol-version mismatch is an error, not a fallback.

Responses use `{ "ok": true, "data": ..., "error": null }` or `{ "ok": false, "data": null, "error": { "code": ..., "message": ... } }`. Server-supplied error text is not blindly displayed by the production client; known categories receive local explanations.

There are **no** `/rpc`, admin, filesystem, file, transfer, event-stream, chat or attachment routes on these listeners. A rejected request may close its HTTP connection; clients must not assume keep-alive after malformed/unsupported requests.

## Authorization and epochs

`PeerPermissions` separates:

- `chat`: reserved domain consent, false by default;
- `attachment`: separately reserved consent, false by default;
- `roots`: at most eight registered root IDs with explicit `browse`, `read`, `create`, `modify`, `trash`, `sync_read` capabilities.

No root is registered by Phase 2. Paths, unknown scopes, duplicate root IDs/capabilities and device-level capabilities inside root grants are rejected. A root grant never grants another root or a different device. Local grants and the remote peer's grants are stored separately.

An authenticated session uses `(peer_id, grant_revision, session_epoch)` obtained from its TLS identity, never trusted from a caller's claimed identity. Each protected request checks active state and current counters. Scoped content authorization additionally checks capability and current root registration.

Permission changes use an expected revision and increment both counters. Revocation commits revoked state, clears grants and increments counters, removes its allowed pin, then cancels registered sessions/workers. Session registration rechecks the pin under the registry lock so a finishing handshake cannot bypass the cancellation sweep. Old trust rows retain their epoch history.

Future file/transfer commits must integrate this gate transactionally with their own operation checks; this build cannot claim tests of nonexistent chunk/commit handlers.

## Reconnect and resource limits

| Control | Implemented value/behavior |
|---|---|
| Local IPC frame | 65,536 bytes; reserve for envelope. Oversized overviews trim only optional history/hints with a notice, preserving active trust/grants. |
| Peer body | 16,384 bytes; bounded body collection; no decompression. |
| Certificate | ≤4096 DER bytes; bounded Base64 claim field. |
| Trust capacity | 16 active/pending peers; capacity check serialized with insertion. |
| TLS connections | Shared 24-slot semaphore; 12 new accepts/second per listener. |
| Session requests | 12/second per connection. |
| Deadlines | TCP 4 s, TLS 5 s, request headers 5 s, request/response body 3 s, response 5 s. |
| Connection lifetime | 60 s; healthy peers/proof waits re-establish with fresh mTLS. |
| Healthy exchange | Every 5 s; no “online” before authenticated health. Inbound status also requires a live session. |
| Retry | At most six consecutive failures; jittered exponential waits with a 30 s base cap. Manual retry resets the attempt series, never the pin. |
| Fatal categories | Identity/capability/version/authorization errors stop automatic attempts. A server that closes before the first authenticated protocol response is flagged for manual review rather than assumed trusted. |
| Invitation expiry | Immediate logical denial; 500 ms cleanup monitor closes bootstrap/pending transports. |
| Windows profile monitor | Five-second inspection interval, three-second OS-query deadline; failure closes the network runtime. Native timing remains to be qualified. |
| mDNS candidates | At most 32 application entries; 60 s freshness; no automatic trust/connect. |
| QR images | PNG/JPEG only, ≤5 MB, pre-decode dimensions ≤4096×4096; decoding canvas ≤2048×2048. |

The mDNS library's own internal behavior, hostile multicast load, real NIC transitions and native firewall timing still need platform/security qualification. No global public-internet transport is introduced.

## Local owner commands

Existing: `get_snapshot`, `save_settings`, `run_diagnostics`, `clear_activity`.

New: `configure_connections`, `start_pairing`, `cancel_pairing`, `approve_pairing`, `reject_pairing`, `join_pairing`, `cancel_join`, `update_peer_permissions`, `revoke_peer`, `reconnect_peer`, `set_peer_endpoint`, `discover_peers`.

The native shell declares these sixteen commands individually in its command manifest and main-window capabilities. Shutdown remains a native lifecycle action, not a browser or peer permission. There is no generic “execute command” frontend bridge.
